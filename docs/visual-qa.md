# 시각 QA

## 기준과 범위

제품 목표는 모바일 브라우저의 iPhone 18 Pro / iOS 27 경험이다. 실제 구현 범위와 완료 여부는 해당 Issue를 따른다. 개발 기반·잠금/홈·앱·시스템 패널의 검증 범위를 구분하고 일부 화면의 통과를 전체 iPhone 경험 완성으로 기록하지 않는다. 실제 iPhone Safari에서 검증한 결과도 아직 없다.

Issue 26부터 사용자가 요청한 실제 iPhone 사용 캡처·조작 영상을 우선 기준으로 삼는다. [실사용 화면과 모션](fluid-motion.md)에 버전과 관찰 범위를 구분한다. 광고 자료로 동일성을 판정하지 않으며, 공식 Apple 사용 설명서의 화면은 앱 구조 비교에 함께 사용한다. 기준 자료는 `references/manifest.json`과 `references/real-device-sources.json`에 등록한다. 커뮤니티 코드는 구조와 표현 기법의 참고 자료다. 가짜 상태바·Dynamic Island는 웹에 그리지 않는다. Issue 30의 최신 요청에 따라 PC에는 중앙 프레임, 모바일에는 전체 화면을 적용하며 각각 경계와 잘림을 확인한다. iOS 18 자료는 보조이며 기존 iOS 스타일을 유지한다.

Issue 30의 고정 장면은 토요일 16:40, 가상 27°, 초기 할 일 3개다. 실제 방문 시각이나 `page.clock` 변경에 따라 데모를 진행하지 않는다. 초기 알림·카레 완료 후 할 일 2개·사진별 배경·PC 프레임을 기존 앱과 함께 검토한다. 게임 이미지·실제 생활 참고 사진·창작 가족 그림을 혼동해 공식 휴대폰 콘텐츠로 표현하지 않는다.

Issue #46의 최신 요구에 따라 홈·앱·시스템 패널·통화의 하단 막대를 표시하지 않는다. 이는 Issue #20의 막대 표시 결정을 대체한다. 기존 하단 터치 영역·safe area·키보드 대체 조작은 유지한다. 제어 센터 자체의 `+`/전원·연결/배터리 줄은 중복 외곽 상태바와 구분한다. 사용자 선택과 공식 원본의 차이는 증거에 명시한다.

공식 잠금·홈 PNG를 직접 열어 확인한 초기 관찰은 다음과 같다. 이는 추후 구현 Issue의 출발점이며 완성된 앱에 대한 검사 결과가 아니다.

| 기준                      | 관찰한 내용                                                                                                |
| ------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `apple-lock-screen-image` | 위쪽 날짜, 세로로 크게 표시된 9:41, 시계 일부를 가리는 회색·금빛 곡선 배경, 아래쪽 원형 손전등·카메라 제어 |
| `apple-home-screen-image` | 위쪽 2×2 사진·캘린더 위젯, 4열 아이콘 4행, 검색 capsule, 아이콘 4개가 있는 glass Dock                      |

구체적 배경·위젯·앱 구성은 구현 Issue의 범위를 따른다. 참고 이미지의 구성을 관찰했다는 이유로 해당 이미지·폰트를 제품에 복사하지 않는다. 자산의 출처와 사용 가능 범위는 별도로 확인한다.

## 실제 비교 절차

1. Issue의 화면·상태·완료 조건과 비교할 reference ID를 고른다. 현재 구현 범위와 다음 Issue의 목표를 나눈다.
2. 실행 환경을 기록한다. OS, 브라우저, viewport, 확대 비율, locale, timezone, 화면 상태를 고정한다. 시간·무작위 값·애니메이션이 비교를 흔들면 테스트 조건에서 통제한다.
3. `/yaku_IPhone/`에서 화면을 실행하고 필요한 조작을 수행한다. 잠금/홈 구현 후에는 초기 진입, 잠금 해제, gesture 취소와 복귀, 키보드 대체 조작을 범위에 맞게 확인한다.
4. 기준 이미지와 결과 캡처를 **직접 열어** 비교한다. 테스트가 통과했다는 출력만 읽고 시각 검토를 완료 처리하지 않는다.
5. 비율·여백·타이포그래피·색·glass·그림자·아이콘·safe area를 살핀다. 오류를 수정한 뒤 같은 조건으로 다시 캡처한다.
6. 최종 캡처를 추적 가능한 경로에 보관하고 확인 조건·실제 차이·남은 제한을 기록한다. 이후 PR의 SHA와 증거를 연결한다.

가독성, 터치 영역, 가로 overflow, 브라우저 UI와의 겹침, reduced motion도 확인한다. 모바일 전용이지만 큰 viewport에서 콘텐츠가 깨지는지 간단히 살핀다. 복잡한 기능이 없는 작은 시각 수정에 구현을 그대로 되풀이하는 단위 테스트를 추가하지 않는다.

## 브라우저와 실제 기기

Chromium과 Playwright WebKit 검사는 엔진 차이·레이아웃·동작 회귀를 찾는다. 모바일 viewport와 터치를 에뮬레이션해도 물리적 iPhone의 Safari·주소 표시줄·safe area·제스처를 완전히 재현하지 못한다.

실제 기기 결과가 없으면 `실제 iPhone Safari 미검증`을 남긴다. 실제 기기를 사용할 수 있을 때 기기·iOS·Safari 버전과 세로/가로 방향, 주소 표시줄 변화, safe area, 터치 제스처, glass 성능을 기록한다. 접근하지 못한 환경을 확인했다고 적지 않는다.

## 기준 이미지와 변경 승인

Playwright 시각 기준 경로는 `tests/visual/baselines/{platform}/{projectName}/`다. macOS의 `darwin`과 CI Linux의 `linux`, Chromium과 WebKit을 분리한다. 폰트·렌더링 차이가 있는 다른 플랫폼의 캡처를 복사해 비교 기준으로 쓰지 않는다.

`npm run test:visual`은 기준 이미지를 자동 갱신하지 않는다. 새 기준 또는 의도한 디자인 변경이 필요하면 해당 OS에서 명시적으로 생성한다.

```sh
npm run test:visual -- --update-snapshots
```

생성 자체가 승인은 아니다. 기존 이미지·새 이미지·diff를 열어 의도한 변경인지 확인하고, 구현을 맡지 않은 검토자가 baseline 변경을 검토해야 한다. PR에는 `baselineChanged: true`와 `baselineReview`를 기록한다. 예상하지 못한 차이나 검사 실패를 숨기려고 새 기준을 받아들이지 않는다.

회귀 검사의 기준 이미지는 이전에 검토한 앱 화면이다. Apple reference는 제품 목표의 비교 자료다. 앱 화면이 이전 캡처와 같다는 사실만으로 Apple UI와 일치한다고 결론내리지 않는다.

## 기록 예시와 제한

검토 기록에는 다음 내용을 포함한다.

- 대상: Issue, 현재 head SHA, 확인한 화면·상태·viewport를 나타내는 `visual.scenes`, reference ID.
- 환경: OS·브라우저·viewport, Node·Playwright 버전, 실제 기기 여부.
- 검사: 실제 명령과 `pass`·`fail`·`not-run`, 구체적인 결과. UI 변경은 `check`·`test:e2e`·`test:visual` 통과 기록이 필요하다.
- 증거: 실제로 연 추적 이미지 경로와 필요하면 CI report 링크.
- 비교: 확인한 요소, 수정한 차이, 의도적으로 남긴 차이와 이유.
- 판정: 현재 Issue 범위의 통과 또는 남은 문제. 독립 검토자는 자신의 검토 범위를 명시한다.

기반 PR은 예를 들어 “scaffold 제목과 설명이 지정 viewport에서 잘림 없이 보임; 공식 Apple 잠금·홈 이미지와 비교하면 제품 UI가 아직 없으므로 해당 일치도는 평가하지 않음; 실제 iPhone Safari 미검증”처럼 기록한다. 이 문장은 예시이며 실제 캡처를 보지 않고 복사해 통과 결과로 사용하지 않는다.

PR의 정확한 JSON 형식과 이미지 조건은 [하네스](harness.md)를 따른다. UI 변경에서 증거를 만들 수 없으면 미완료 상태를 유지하고 원인을 기록한다. 빈 이미지나 형식만 맞춘 승인으로 gate를 통과시키지 않는다.

## 설정·Safari 장면

Issue 14에서 설정 목록, 다크+130% 글자, Safari 시작/시작 안내/두 탭의 최초 회귀 기준을 추가한다. 기본 목록·시작·안내는 세 viewport의 두 엔진, 다크 설정·두 탭은 390×844 두 엔진으로 총 22장이다. 기존 잠금/홈 18장은 그대로 유지한다. macOS/Linux는 각 실행 환경의 캡처로 따로 검토·등록한다.

주소 편집 중 축소 viewport, 오프라인 안내, 외부 주소 안내, 페이지 메뉴는 별도 직접 캡처와 동작 검사로 확인한다. 단순 viewport 축소를 실제 소프트 키보드 표시 검증으로 기록하지 않는다. 페이지 메뉴를 연 상태에서도 공통 홈 버튼과 스와이프가 가능해야 한다.

## Issue 20 시스템 패널 장면

위 표의 막대 표시 항목은 Issue 20의 당시 기준이다. Issue 46부터는 막대가 사라진 홈·설정·Safari·최근 앱·제어 센터·통화 화면을 확인하며, 빈 하단 영역의 입력과 safe area는 그대로 유지되어야 한다. 48~64px 직선 상승의 현재 앱 축소·이전 앱 미리보기, 옆으로 시작해 위로 꺾는 곡선, 사분원 곡선, 최근 카드의 곡선 삭제를 실제 조작으로 확인한다. 96px 미만 카드 이동은 삭제하지 않고 복귀해야 한다. 버튼 안에서 9px 움직인 탭으로 뒤로·홈·최근 앱 닫기·제어 센터 닫기·Safari의 닫기/취소/뒤로/완료·통화 종료를 검사한다.

390×844 등 기존 모바일 세 크기와 작은 높이, 큰 글자, 키보드 포커스, reduced motion 상태를 포함한다. 기존 baseline을 변경할 때에는 막대·패널 구조 변화가 변경 이유인지 확인한다. 기본 화면의 큰 제목·상시 닫기 X·설명 바가 사라져도 sr-only 제목과 포커스 시 대체 조작의 접근성은 검사한다. 설정 본문의 세로 스크롤, 나머지 화면의 세로 고정과 모든 지원 조작 도달 가능성을 함께 확인하며, 잘라 숨긴 내용을 접근 가능하다고 기록하지 않는다.

공식 이미지 복사 대신 CSS로 재현한 형태·재질을 검토한다. 가상 연결·음량 등의 상태와 실제 OS 제어는 구분한다. iOS 27 알림 센터의 전체 화면·빈 상태가 직접 확인되지 않았다는 제한, 실제 iPhone Safari 미검증을 증거에서 누락하지 않는다.
