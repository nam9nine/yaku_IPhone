# Issue 61 — 메시지 앱과 Mac 모델 연결 검증

검증일: 2026-10-25 KST. macOS 26.5.2 arm64, Node 24.22.0, Playwright 1.64.1. 데스크톱 Chromium·WebKit의 모바일 viewport 검사이며 실제 iPhone Safari는 미검증이다.

## 자동 검사

- `npm run check`: TypeScript·lint·format·단위 검사 351개·production build·harness 통과.
- `PYTHONPATH=ai python -m unittest discover -s ai/tests -v`: 78개 통과. 서버 대역을 사용한 인증·소유권·작업 복구·단일 모델 직렬 처리 계약과 실제 loopback 준비 확인을 포함하며 GPU 성능 검사와 구분한다.
- `ruff check ai`, `ruff format --check ai`: 통과.
- `npm run test:e2e -- --workers=4`: 최종 통합 production build에서 482개 통과. 새 채팅 검사 20개는 HTTPS API 대역을 사용한다.
- `npm run test:visual -- --workers=4`: 224개 통과. 기존 승인 기준을 유지하고 baseline 허용 오차를 바꾸지 않았다.

기존 작은 화면 검색 검사 4개가 실패하여 조사한 결과, 새 앱으로 가로 목록이 길어졌을 때 키보드 포커스가 화면 밖에 남는 결함을 발견했다. 별도 #60에서 수정·검토한 뒤 통합했으며 최종 전체 동작 검사는 통과했다. 입력창 focus·viewport 축소 뒤 최신 답장도 화면에 남도록 확인했다.

## 화면 직접 검토

`issue-61/`의 캡처는 고정 API 대역으로 대기·완료 상태를 만든 production UI다. 생성 모델의 답변이나 품질 증거로 사용하지 않는다. 360×800, 390×844, 430×932 및 390×420을 확인했다. locale `ko-KR`, timezone `Asia/Seoul`, reduced motion을 사용하고 답장 시각은 고정했다. 축소 viewport는 실제 iOS 키보드 재현이 아니다.

직접 연 비교 자료는 `idb-messages-ios27`의 실제 사용 튜토리얼 캡처와 `apple-messages`의 대화 화면이다. 중앙 아바타·이름, 왼쪽 뒤로 버튼, 수신 회색/발신 녹색 말풍선, 하단 둥근 입력칸의 기존 배치를 유지했다. API 대기 상태는 회색 점 세 개로 표시하고, 전송 가능한 화살표는 녹색으로 표시한다. 기존 장보기 선택지는 사용할 수 있을 때 입력칸 위에만 표시해 작은 높이의 대화 공간을 확보했다.

가로 넘침·입력/전송 버튼 잘림은 확인한 크기에서 발견하지 못했다. 한글 조합 중 Enter는 보내지 않고 Shift+Enter는 줄바꿈한다. 긴 입력은 최대 120px 안에서 스크롤하고, 키보드에 해당하는 높이 변화 중 최신 답장을 보존한다. OS와 앱 설정의 동작 줄이기를 모두 적용한다.

제한: 기존 데모 상태바와 사용자 지정 하단 여백을 유지한다. iOS의 모든 메시지 메뉴·첨부·실제 SMS/iMessage를 구현한 것은 아니다. 서버 연결 창은 이 체험의 설정 기능이며 iOS 기본 메뉴와 동일하다고 주장하지 않는다.

## 독립 리뷰에서 수정한 문제

- 저장 실패 때 작업이 영원히 생성 중으로 남는 문제: 제한된 종료 상태 복구와 정리 경로를 보장했다.
- 예약 제어 토큰이 후속 대화 입력을 망가뜨리는 문제: 접수·저장 전에 같은 입력 형식으로 검사한다.
- 새로고침 뒤 실패한 새 요청에 이전 성공 문자를 잘못 연결하는 문제: 서버가 해당 작업의 원문·UUID·접수 시각을 반환하고 job ID로 이력을 연결한다.
- AI 전송 실패가 고정 스토리 답변으로 바뀌는 문제: 실제 성공 이력에서만 스토리를 진행하고 AI 응답 출처를 저장한다.

## 실제 Mac 모델과 HTTPS 왕복

9B 기본 모델 한 개를 Mac의 전용 추론 스레드에 올리고 Cloudflare 임시 HTTPS 터널을 통해 요청했다. 로컬 production 화면에서 Chromium·WebKit 각각 하루카·마지마에게 직접 입력해 실제 답장 4개를 받았고, 두 브라우저 모두 새로고침 후 하루카의 같은 대화를 복원했다. API 대역·응답 치환은 사용하지 않았다. 전송부터 화면 확인까지 2.37~5.95초였으며 표본 4개에 대한 관찰로 성능 보장을 뜻하지 않는다.

`live-*-reply.png` 4장은 위 실제 응답 화면이다. 조정 에이전트가 직접 열어 말풍선·입력칸·긴 답장·하단 버튼을 확인했다. 기존 14개의 고정 API 캡처와 실제 모델 캡처를 구분한다. 실제 응답에는 어색한 말투와 불필요한 추측이 있어 인물 품질 통과로 판정하지 않는다. 학습 어댑터는 문맥·지식 범위의 일부 회귀 때문에 채택을 보류하고 기본 모델을 체험용으로 사용한다.

실제 HTTPS API 감사에서도 11개 조건을 확인했다. Pages origin의 CORS, 미인증 이력 거부, 다른 origin 거부, 방문자별 토큰 발급, 같은 UUID의 중복 작업 방지, 다른 방문자의 작업 조회 404, 실제 모델 생성, 정확히 한 쌍의 이력 저장, 다른 방문자·인물의 빈 이력, 완료 후 재전송의 동일 작업 반환이 통과했다. 이 결과는 프로그램 접근 제어의 관찰이며 모델의 사실성·말투 평가를 대신하지 않는다.

실행 환경의 HTTP 프록시 때문에 로컬 준비 상태 확인이 다른 경로로 전달되는 문제가 실제로 발견됐다. 실행기가 자신이 띄운 127.0.0.1 API에 직접 연결하도록 수정하고, 실패하는 환경 프록시를 설정한 실제 loopback HTTP 테스트로 재현·검증했다. 외부 HTTPS 터널 요청의 설정을 바꾸지는 않는다.

공개 Pages 화면의 최종 배포 왕복은 병합 후 별도 확인한다. 위 관찰은 로컬 UI와 공개 HTTPS API 사이의 왕복이며 실제 iPhone Safari 검증은 아니다.
