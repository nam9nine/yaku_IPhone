# Issue #133 문자 대화의 자연스러움

## 목표

키류 답장 선택지와 하루카·마지마 AI 문자의 흐름이 부자연스럽다는 피드백을 프롬프트 문구 수정이 아니라 입력 맥락·프롬프트 구조·생성 방식·선택지·발신 타이밍 단위로 개선한다. 응답 속도는 판단 기준에서 제외한다(사용자 결정, 2026-11-02).

## 관찰한 원인

운영 DB 사본(2026-11-02 18:57 백업)의 집계와 v34 실제 입력을 확인했다. 원문은 저장소에 옮기지 않는다.

- 모델 입력에 방문자가 보는 도입 문자와 로컬 후속·선제 문자가 대화로 들어가지 않는다. 첫 `안녕`·`네`를 갑작스러운 연락으로 받아들인다.
- 시스템 입력의 대부분이 추상적인 금지 규칙이고, 장면·목적·말투 예시는 적다. 현재 문자는 빈 참고 JSON 봉투에 싸인다.
- 같은 첫마디·말버릇(`갑자기`, `키류쨩`, `와,`)이 반복되고, 짧은 대답을 나무라거나 답할 수 없는 질문으로 끝난다.
- 하루카 선택지가 UI 표현이고 직전 확인 문자에 답하지 않는다. 다이고 첫 선택지는 직전 질문과 맞지 않는다.

## 근거로 삼은 선행 연구

- 지시 개수·위치: ManyIFEval(arXiv 2509.21051), IFScale(2507.11538), Lost in the Middle(2307.03172), 지시 drift(2402.10962).
- 부정 지시의 한계와 반복 강화: 부정 프롬프트(Jang et al. 2023), Pink Elephant(2402.07896, 2503.22395), Learning to Break the Loop(2206.02369), Antislop(2510.15061).
- 역할극: given circumstances(CoSER 2502.09082), 사고 과정의 역할 이탈(2502.16940, 2506.01748), 과장(CoMPosT 2310.11501), 작별 조작(2508.19258).
- 대화 흐름: Opening up closings(Schegloff & Sacks 1973), 질문 비율(See et al. 2019: 너무 적어도 많아도 평가가 떨어진다), 후속 질문(Huang et al. 2017: 호감을 높인다). 질문을 없애지 않고 연속만 막는다.
- 선택지: 인접쌍과 긍정 편향(Mieczkowski et al. 2021, Arnold et al. 2018, Robertson et al. 2021), 선택 인정(Fendt et al. 2012), choice poetics(Mawhorter et al. 2014).
- 평가: ACUTE-Eval(1909.03087), PingPong(2409.06820), CharacterEval(2401.01275), LLM 판정 편향(2306.05685).

## 범위 변경 (2026-11-03 사용자 결정)

하루카와는 채팅하지 않고 마지마·키류의 말·다테 같은 인물에 집중한다. 이미 들어간 하루카 관련 수정(선택지 문구, 사건 모드 저장 검증 버그)은 유지하고, 하루카 AI 답장 추가 조정은 하지 않는다. 하루카 AI 답장 제거와 다테 대화 추가는 별도 Issue로 제안한다.

## 단계

1. 공유 도입 문자 카탈로그와 이벤트별 실제 로컬 문구를 서버가 같은 순서의 대화 턴으로 재구성한다. API 형식은 바꾸지 않는다.
2. 작성 프롬프트를 인물 → 말투 예시 → 지금 상황 → 문자 주고받기(긍정형, 이유 포함) → 지켜야 할 것 → 자료 → 이번 답장 순서로 재구성한다. 일반 문자는 현재 문자를 원문 그대로 마지막 user 턴에 둔다. 사건 판정·상태 규칙은 유지한다.
3. 여러 후보를 생성하고 코드 검사(짧은 대답 꾸중, 반복 첫마디·말버릇, 질문 연속, 메타 표현, 번역투 대명사)를 통과한 후보 중에서 고른다. 동률은 별도 판정 호출로 고른다.
4. 하루카 선택지를 직전 확인 문자에 답하는 키류 말투 두 가지로 바꾸고 한 번에 한 할 일만 보인다. 다이고 선택지를 직전 문자에 맞춘다.
5. 서버 선제 초대가 진행 중인 대화 직후에 끼어들지 않게 한다.
6. 합성 다중턴 상황으로 기존(v34)과 신규 출력을 실제 모델에서 생성해 자동 지표와 블라인드 비교로 판정한다.
7. 독립 검토(백엔드·프런트·정책) 지적을 반영한다: 서버 이력에 사용자 턴별 이벤트를 실어 로컬 문자를 처음 보고된 자리에 두고, 모델 장애·시간 초과는 후보 생성을 바로 멈추며, 되묻는 `네?`·웃음·`그렇군요`를 동의로 읽지 않고, 볼링 사건 답장에는 장면 대신 말투 예시만 넣고 짧은 답의 뜻은 사건 과제에 맡긴다. 성적 요청 범위의 피해 이야기·우회 요청 문구, 틀린 전제·약속과 완료 구분을 되살린다. 감사 기록은 렌더링한 도입·로컬 문구를 저장한다. 하루카 선택지 두 개는 할 일을 직접 말한다. 같은 ID로 바뀐 선택지는 예전 문구에 예전 답장이 이어지게 한다. 사건 모드에서 장보기를 끝낸 하루가 새로고침에 초기화되던 기존 검증 버그도 고친다.
8. 2차 독립 검토 지적을 반영한다: 볼링 사건 답장에서도 초대·통화 후속을 보낸 순서의 턴으로 넣고, 입력 예산 축소 때 첫 남은 턴이 답한 문자를 남기며, 동률 판정은 일반 답장에만 쓴다. 꾸중·메타·탓하기 검사의 오탐과 누락을 줄이고, 마지마의 겁주기·위치 아는 척 금지와 `성적 역할극` 문구를 되살린다. 하루카 선택지는 모두 할 일을 직접 말하고 최근 확인 문자부터 보인다.
9. 검토 반영 뒤 버전(v37)을 평가한다. `그렇군요` 뒤 꾸중이 남으면 턴 안내·장면에서 '짧다'는 묘사를 빼고, 모든 후보가 꾸중으로 탈락할 때 불평 문장만 빼는 안전장치를 둔다.
10. 최종 버전(v39)을 다시 평가해 v34와 블라인드 비교한다. 검토 전 초안(v35)과 중간 버전(v36–v38)의 결과는 원인 분석에만 쓴다.

## 검증

- Python 단위 테스트 전체, `npm run check`, 관련 e2e·visual.
- 자연스러움 평가: 같은 상황·같은 방문자 문자에서 v34와 신규를 비교한다. 실패와 판단 근거를 그대로 기록한다.
- 볼링 사건 평가로 사건 판정 회귀를 확인한다.

## 불확실성

- 프롬프트 형식 변화의 효과는 모델마다 다르다(Sclar et al. 2023). 실제 출력 비교 전에는 개선으로 기록하지 않는다.
- LLM 판정은 팬 검수가 아니다. 마지마 호칭(`키류쨩`/정발 `키류야~`)은 소유자 결정 사항으로 남긴다.
- 후보 생성은 대기열 시간을 늘린다. 사용자 결정에 따라 속도는 기준에서 제외하지만 실제 소요 시간은 기록한다.
- 마지마에게 직접 건 짧은 통화 뒤 앱이 붙이는 로컬 문자는 문구가 모델에 전달되지 않는다(이벤트 설명만 전달). 문구별 이벤트 ID는 서버가 먼저 배포돼야 해서 후속 작업으로 남긴다.
- 하루카 AI 답장을 기다리는 동안 다른 할 일을 체크하면 화면과 모델 입력의 순서가 한 칸 어긋날 수 있다. API에 체크 시각이 없다.
