# Issue 129 — 사건 발신의 제안과 합의 구분

## 문제와 범위

Issue 123의 공개 실제 Gemma 확인에서 날짜 없는 초대 뒤 사용자 무응답만 있었는데 통화 후속 문자가 날짜를 확정해 말했다. UI 연락 순서는 통과했지만 내용 실패다. 원문·입력·실행 결과를 보존하고 사건 기능은 OFF로 되돌렸다. 일반 채팅은 유지한다.

사건 초대와 통화 후속의 발신 입력에서 확인된 사실, 인물의 미결 제안, 사용자의 합의를 구분한다. 근거 없는 일정·예약·이동·승패 확정을 막되 실제로 제안되거나 합의된 날짜는 사용할 수 있어야 한다. 특정 단어 차단·모든 날짜 금지·사건별 정답 문구는 추가하지 않는다.

2026-10-31 KST의 연결 검사에서 일정 변경을 최종 답장은 반영했지만 reader가 전체 취소로 판단하여 DB도 닫히는 문제가 확인됐다. 기존 조건의 철회·교체와 활동 자체의 취소를 구분하는 reader 계약 보완을 범위에 추가한다. 첫 18개 발신 검사와 연결 실패는 보존하고, 변경된 reader는 기존 12상황 전체와 정정·취소 연결을 다시 검증한다. UI와 DB 스키마는 변경하지 않는다.

## 검증과 완료

- v22 전체 검사에서 12상황 중 4상황만 내용 기준을 충족했다. 미정 시간의 참여 수락, 결정 보류, 다른 활동의 거절을 잘못 해석했고 일부 답장은 최신 문자 대신 이전 질문에 답했다. 잘림 2건과 근거 없는 준비·일정도 남았다. 사용자의 추가 요청에 따라 알려진 오류를 남긴 채 원래 10/12 수치만으로 배포하지 않는다.
- 같은 입력을 고정한 reader·writer·후속 문자 A/B를 분리한다. 생성 완료와 의미·형식 통과를 구분하고, 개별 실험의 설정·분모를 섞지 않는다. writer 숙고 상한만 낮춘 결과는 최신 질문 오인과 형식 오류가 남아 채택하지 않는다.
- 다음 구현은 사건 reader의 불필요한 답장 초안 출력을 제거하고, 이전 상태와 최신 발화를 구분한다. 사건 답장 writer는 실제 최신 문자를 마지막 user로 전달하며 질문에 선택된 근거와 자동 사건 배경을 분리한다. 실제 이력 이외의 가상 대화쌍은 만들지 않는다.
- 사건 통화 후속에만 짧은 숙고 256·총 출력 상한 512를 시험한다. 일반 후속 96·non-thinking과 일반 답장 프로필은 유지한다. 하나의 모델·FIFO를 유지하고 실제 생성 설정을 실행 기록에 남긴다. 네 개 고정 후속 사례의 개선은 최종 통과가 아니며 전체 발신·다중턴 재검사가 필요하다.
- [Gemma 공식 입력 형식](https://ai.google.dev/gemma/docs/core/prompt-formatting-gemma4)을 2026-10-31 다시 확인했다. 단일 system과 실제 user/model 턴, 이전 사고 내용 제외라는 기본 계약을 유지한다. 이 문서는 응용 프롬프트의 한국어 대화 품질을 보장하지 않는다.
- v23 실제 진단에서도 부상 제약을 거절로 읽거나 다른 활동의 거절을 현재 사건에 적용하는 오류가 남았다. 다음 버전은 실제 초대·대화·통화 결과·현재 문자만으로 작은 사건 해석을 수행하고, 원작 RAG의 근거 읽기와 분리한다. 분류에는 대상과 의사·일시적 제약을 구분한 짧은 구조화 결론을 사용한다. 모델은 하나이며 호출은 순차다. 별도 호출의 실제 지연과 토큰은 측정하고, 이를 미리 성능 향상으로 표시하지 않는다.
- 여섯 기존 진단 외에 명시 취소·부상 중 참여·다른 활동 수락·설명 요청·이동과 완료 구분 등 반대 조건 10개를 생성 전에 고정한다. 입력 단어 분기나 사례별 정답을 넣지 않는다. 호칭·관계는 자료에 적힌 화자와 상대 범위를 보존하며 다른 인물의 말투 금지로 확대하지 않는다.
- v23 발신 18개에서도 합의 오인과 작성 메모·잘림이 남았다. 사건 후속의 256/512 설정도 아직 배포 후보이며, 고정 입력에서 자연스러운 사고 종료와 충분한 총 출력 예산을 비교한 뒤 최종 설정을 정한다.
- [Gemma 4 모델 카드](https://ai.google.dev/gemma/docs/core/model_card_4)의 권장 sampling은 temperature 1.0, top-p 0.95, top-k 64다. 해석기의 temperature 0은 프로젝트 실험 설정이며 공식 기본값으로 표현하지 않는다. [고정 llama.cpp b11669의 Gemma 파서](https://raw.githubusercontent.com/ggml-org/llama.cpp/b11669/common/parsers/gemma4.cpp)는 구조화 응답 앞의 선택적 사고 채널을 허용한다. 사고가 관찰되지 않았다는 결과만으로 JSON schema가 사고를 차단한다고 결론 내리지 않는다.

- 초기 발신 전용 수정의 일반 답장·reader 입력은 5문맥에서 이전 코드와 동일했다. 이후 reader 변경의 성능을 이 비교로 대신하지 않고 새 버전의 12상황을 실행한다.
- 수정 발신 뒤 실제 다중턴 연결을 확인하고, 새 출력·입력·모델·프롬프트 버전과 소스 해시를 기록한다.
- 기존 full-v4의 12상황 중 10개 통과는 당시 코드의 개발 평가로 유지한다. 새 평가와 분모를 합치거나 새 SHA 전체 성능으로 바꾸지 않는다.
- 공통 검사·필수 CI·독립 내용 검토 후 squash 병합한다. 수정 서버를 OFF로 배포하고 새 공개 검증에서 실제 연락 흐름과 내용을 확인한 뒤 활성 상태로 완료한다.
- Issue 123의 공개 검증 완료까지 연결한다. 팬·실제 iPhone 확인은 관찰 없이 통과로 표시하지 않는다.

## 대화 해석의 추가 진단

v25의 실제 입력 진단에서 단순한 JSON 순서 변경, 인용 추가, 일반 분류 예시, 같은 모델의 주장 재검증만으로는 다른 활동의 거절을 이번 제안에 적용하는 오류를 없애지 못했다. 의미 요약이 충실해도 뒤의 분류가 틀린 사례가 있어, 요약 정확도와 상태 변경 정확도를 따로 평가한다. 기존 16개는 이미 반복 사용한 개발 자료이며 미사용 평가 자료로 표현하지 않는다. 별도로 고정한 8개는 후보를 확정할 때까지 사용하지 않는다.

단일 요약을 별도 호출로 분류하는 진단도 실패를 남겼다. 다음 비교는 현재 발언을 주체·활동·부정·조건이 연결된 명제로 나누고, 명제별 판단을 적용하는 방법이다. 서로 다른 활동은 분리하되 같은 약속의 조건 철회와 대체는 연결을 보존한다. 활동명을 문자열로 비교하는 분기나 사례별 정답은 넣지 않는다. 부상·일시적 사정처럼 활동명을 생략한 참여 제약과, 명시된 다른 활동의 거절을 모두 검사한다.

[Schema-Driven Prompting 연구](https://aclanthology.org/2021.emnlp-main.404/)의 스키마 설명과 대화 상태 구분을 설계 참고로 사용한다. 해당 연구는 여기의 Gemma·한국어 문자·양자화 조건을 검증하지 않았다. 분리한 모델 호출도 같은 오류를 공유할 수 있으므로 실제 명제 충실도, 최종 전이, 놓친 상태 변경, 지연·실패를 각각 확인하기 전에는 채택하지 않는다. 중간 독해는 대화 원문·RAG·장기 기억으로 저장하지 않는다.

명제별 실제 검사도 상태 12/16에 그쳐 채택하지 않았다. 다음 후보는 이미 고정된 native 입력과 일반 예시 입력을 같은 모델에 순차 적용하고, 엄격 검증을 통과한 두 canonical 전이가 정확히 같을 때만 상태 변경을 허용한다. 불일치와 호출 실패를 구분하며, 합의되지 않은 세부 행위를 어느 한쪽에서 가져오지 않는다. 기존 16개에서는 사후 조합으로 일치 15개와 보류 1개가 나왔다. 이는 16개 의미를 모두 이해했다는 결과가 아니다.

[LLM 대화 상태의 확신도 연구](https://arxiv.org/abs/2409.09629)는 불확실한 결정의 확인과 검증된 신뢰도 측정이 필요함을 설명한다. 이번 두 입력의 일치는 그 연구의 보정된 확신도나 독립 검증을 구현한 것이 아니다. 같은 모델이 같은 오류에 동의할 수 있고 명확한 결정을 놓칠 수도 있으므로, 잘못 허용한 변경과 놓친 변경을 모두 평가한다. 처음 사용한 별도 8개는 의미를 암시하는 식별자 문제가 발견되어, 내용·정답·정책은 그대로 두고 불투명 UUID를 사용한 인코딩 비교를 추가한다. 같은 문제를 새로운 8개로 다시 세지 않는다.

## 일상 IF와 상태 효과의 구분

v26 실제 다중턴 실행에서 전면적인 행동 창작 금지는 소소한 개인 일상까지 제한했다. 다음 버전은 답장에 한해 인물 혼자의 사소한 생활 배경·기분·취향을 기존 대화와 모순되지 않게 정하도록 한다. 원작, 다른 사람의 행동·의도, 공동 약속·이동·활동 결과·승패, 자신의 위치 변경과 연락·예약·구매는 계속 근거를 요구한다. 이 범위는 운영자의 기본 설계 판단이며 새 팬 검수나 사용자의 추가 확정으로 표시하지 않는다. 일반 채팅·초대·통화 후속의 기존 입력은 바꾸지 않는다.

이전 엄격 기준의 실패는 보존하고 새 기준으로 소급 통과시키지 않는다. 새 문자 생성 비교 19개(기본 16개 중 실제 첫 답변에 이어지는 질문을 별도 단계로 실행, 추가 보호 경계 3개)와 기존 개발 사례 2개를 분리한다. 실제 첫 답변을 후속 질문에 전달하고 원래 예시 답변을 대신 넣지 않는다. 분류·검색 결과를 고정 공급하는 문자 생성 진단과 전체 API·DB 다중턴 검사를 구분한다.

사건 해석 두 결과의 `defer`와 `change_topic`은 실제 저장소에서 같은 보류 효과를 가진다. 현재 사건·버전·근거를 각각 검증한 뒤 이 두 결정만 `defer`로 합친다. 원래 출력과 서로 다른 의미는 그대로 기록하고 합의된 세부 행위는 없는 것으로 둔다. 수락·취소·거절 등 다른 불일치는 계속 보류한다. 종료된 사건은 보류·화제 전환으로 다시 열지 않으며, 명시적 수락만 기존 재개 경로를 사용할 수 있다. 저장된 상태와 writer에 보여 주는 상태를 같은 조건으로 계산한다.

미확정인 것은 현재 문자 해석이다. 이미 기록된 수락이나 종료까지 미정으로 되돌리거나, 수락한 참여 여부를 다시 확인하도록 강요하지 않는다. 반대로 설명을 허락했다는 이유만으로 참여가 확정된 일정 협의를 시작하지 않는다.

## v28: 실제 대화가 들어갈 공간과 발화의 확정 정도

v27의 문자 생성 진단은 21개 중 통과 12개·부분 5개·실패 4개였다. 기존 원문을 질문의 전제에 맞춰 뒤집거나, 검토 중인 제안을 합의로 확정한 실패를 보존한다. v28은 사건의 사용자 답장에만 짧은 인물 프로필을 사용하고 중복 지침을 교체한다. 질문 전제와 새 보고·정정, 제안·검토와 합의, 참여 수락과 세부 조건 확정, 예정과 완료를 구분한다. 원작 관계·사건 근거는 기존 자료로 유지한다. 이번 v28 변경은 API·DB·해석기·검색 reader·모델 설정·일반 채팅·선제 발신·통화 후속 입력을 바꾸지 않는다.
