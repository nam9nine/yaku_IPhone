# 문자 대화의 검색·장기 기억·인물 입력

이 구현은 DB 원문을 검색해 매 요청의 모델 입력으로 조립한다. Gemma 가중치가 대화를 학습하거나 모델 프로세스가 방문자별 기억을 갖는 구조가 아니다. 같은 방문자가 다시 접속하면 SQLite의 같은 범위를 읽고, 필요한 원문을 다시 입력한다.

## 선행 연구와 이번 선택

[LongMemEval §4–5](https://arxiv.org/html/2410.10813v2)는 장기 기억을 색인·검색·읽기로 나눠 비교한다. 대화 전체 하나보다 더 작은 단위를 저장하고, 검색 키와 질문을 개선하며, 찾은 내용을 어떻게 읽힐지 구분한다. 정보 추출 외에도 여러 세션을 연결하는 추론, 시간 추론, 정보 갱신, 모르는 정보에 답하지 않기를 평가한다. 이번 구현 역시 검색 성공과 답변의 문맥 이해를 별도 검사한다. 논문의 사실 추출 키 확장·시간 범위 추출·chain-of-note 전체를 재현한 것은 아니다.

| 방식                  | 이번 구현에서의 선택과 이유                                                                                                            |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| 최근 대화만 넣기      | 최근 여섯 교환을 native user/assistant 턴으로 유지한다. 이것만으로는 이전 대화를 기억할 수 없으므로 원문 검색을 추가한다.              |
| 전체 과거 대화 넣기   | 6,144토큰의 운영 문맥 한도 때문에 기본 방식으로 쓰지 않는다. DB 원문은 모두 보존하고 입력에서만 선택한다.                              |
| BM25 + embedding      | 고유명·제품명·확인 문구의 정확한 일치와 다른 표현의 의미 유사도를 함께 본다. SQLite FTS5와 CPU E5 점수를 RRF로 합친다.                 |
| 문맥을 붙인 청크      | 원작 장면에 게임·당시 맥락·화자를 유지하고, 기억 검색 후 앞뒤 원문 교환을 함께 전달한다. 매번 LLM으로 설명문을 만들어 저장하지 않는다. |
| 요약·사실 추출 메모리 | 현재 미사용. 추출된 해석이 원문을 덮거나 제안을 완료 사실로 바꿀 위험과 추가 생성 지연을 먼저 측정해야 한다.                           |
| 관계·시간 그래프      | 현재 미사용. 이후 여러 사건의 유효 기간과 인물 관계를 연결할 필요가 실제 평가에서 확인되면 검토한다.                                   |

[Anthropic Contextual Retrieval](https://www.anthropic.com/research/contextual-retrieval)은 청크가 원문에서 무엇을 가리키는지 설명을 붙여 embedding과 BM25를 만들고, 결과를 합치는 방법을 다룬다. 현재 코드는 문맥 보존과 두 검색 경로의 결합을 사용하지만, 전체 문서를 LLM에 보내 청크별 설명을 생성하거나 별도 reranker를 실행하지 않는다. 자료에 이미 있는 화자·장면 맥락을 우선한다. Anthropic의 검색 개선 수치를 한국어 문자 서비스 성능으로 가져오지 않는다.

[Mem0 §2](https://arxiv.org/html/2504.19413v1)는 대화에서 중요한 정보를 추출하고 기존 기억을 갱신하는 방식이며 그래프 변형도 비교한다. 단순 원문 검색보다 짧은 기억을 제공할 수 있지만, 추출·수정 판단이 별도 시스템 작업이 된다. 이번에는 생성 호출을 답장 한 번으로 유지한다. 원문 검색이 추출 메모리보다 낫다는 실험 결과가 있다는 뜻은 아니다.

[Zep §2–3](https://arxiv.org/html/2501.13956v1)는 사건·개체·사실을 연결하고 시간에 따라 관계의 유효성을 관리한다. 현재 `correction_links`는 이런 시간 그래프가 아니다. 원문에서 정정 후보를 찾아 함께 보여주는 규칙이며, 사실이 언제부터 참인지 판정하거나 폐기하는 LLM·그래프 상태를 저장하지 않는다.

## 실제로 무엇을 색인하는가

### 방문자의 대화

`ChatDB.history(visitor, character, scenario)`가 반환한 정상 교환만 받는다. 접수됐지만 실패한 요청, 잘린 출력, 검토 메모와 개선 답안은 기억 후보가 아니다. 범위 필드가 있는 행은 입력 범위와 다르면 거부한다. 필드 없는 행은 반드시 위 DB의 범위 지정 조회 결과여야 한다. 전체 DB를 가져와 나중에 인물을 거르는 호출 방식은 허용하지 않는다.

검색 키는 사용자 한 턴과 그 답장 한 턴의 원문이다. 검색 후 읽기에 사용할 값은 그 교환과 앞뒤 교환이다. 최근 여섯 교환은 이미 실제 대화로 들어가므로 이전 부분만 별도로 검색한다. 최대 두 구간을 전달한다. 현재 문자만으로 찾은 첫 후보를 우선 확보하고, 최근 두 교환을 포함한 문맥 질의로 두 번째 후보를 보완하며 중복을 제거한다. 반복된 최근 잡담이 현재 주제를 밀어내는 실제 진단 실패를 확인해 적용했다. 지시어 질문은 문맥 후보가 보완하며, 첫 후보도 의미 해석의 정답을 보장하지 않는다. SQLite 원문은 지속 보관되지만 현재 FTS 색인은 요청마다 허용된 후보로 구성하고 E5 passage 벡터는 프로세스의 제한된 캐시에 둔다. 영구 벡터 색인이나 모든 사용자 대화의 전역 검색은 구현하지 않았다.

### 원작 자료

`ai/chat/registry.json`은 22개 사실과 4개 장면의 좁은 채택 목록이다. 1,201개 전 시리즈 참고 청크의 원본·`runtime_eligible=false`는 바꾸지 않았다. 전 시리즈 모든 사건을 두 인물이 기억한다고 표현하지 않는다.

각 항목에는 출처 URL·원본 SHA·해당 부분의 좌표·발췌문 SHA·허용 인물·IF·채택 사유를 둔다. 공식 소개의 관계·생활 배경, 넓은 스토리 원문 중 허용한 문장, `train`에 속한 판단/말투 장면을 구분한다. `valid/dev/test` 분할의 원작 발화는 등록 자체를 거부한다. 카드의 문자 말투와 상황별 적용 규칙은 창작 IF 해석이며 팬 승인으로 표시하지 않는다.

장면에는 원래 상대가 니시다·시마노인 경우 그 화자 그대로 남는다. 이 발화를 키류에게 했던 문자로 바꾸지 않는다. 출처에서 대화 수신인이 별도로 검증되지 않았다면 `recipient_status=unresolved`를 유지한다.

## 질문에서 검색 결과까지

`ChatPromptBuilder.build`는 방금 받은 문자와 최근 두 교환으로 검색 질문을 구성한다. 새로운 문자부터 배치하므로 E5의 512토큰 한도를 넘더라도 현재 질문을 먼저 읽는다. 인물·IF·실행 승인 필터를 통과한 자료만 FTS와 embedding 입력으로 보낸다.

한글 조사와 인명 별칭을 보완한 BM25 순위와 E5 cosine 순위를 RRF로 결합한다. E5는 `intfloat/multilingual-e5-small@614241f622f53c4eeff9890bdc4f31cfecc418b3`, 공식 FP32 ONNX, CPU provider, masked mean pooling과 L2 정규화다. `query:`와 `passage:` 접두부를 구분한다. 운영용 hybrid 경로에는 `E5Onnx`를 명시적으로 전달해야 한다. encoder가 없는 테스트/진단 경로는 메타데이터에 `bm25-only`라고 기록되며 hybrid 검증으로 표시하지 않는다. [모델 사용법](https://huggingface.co/intfloat/multilingual-e5-small)

현재 semantic 임계값 0.84는 프로젝트 초기 설정이다. 이 값이나 원시 cosine을 정확도·확신도로 해석하지 않는다. lexical 결과가 없고 semantic 임계값도 넘지 않으면 빈 결과를 유지한다. 사실 최대 3개, 장면 최대 1개를 선택하며 후보가 부족하다고 무관한 행으로 채우지 않는다. 별도 신경망 reranker·HyDE·LLM 질문 재작성은 없다.

## 정정·취소와 모델이 읽는 내용

예를 들어 30턴 전에 `카레 사자`가 있고 이후 `카레 말고 우동으로`가 있으면, 카레가 검색되더라도 그 뒤의 정정 후보를 전체 같은 범위에서 다시 확인한다. 검색 상위 두 개 안에 정정이 없다는 이유로 무시하지 않는다.

현재 코드는 `말고/아니라/취소/바꿔/정정` 등의 표시를 찾는다. 원래 교환의 사용자·인물 양쪽 발언에서 주제를 추출하며 관련 주제 단어가 겹치면 `lexical-link`, `그거` 같은 지시어가 직전 교환의 같은 주제를 가리킬 가능성이 있으면 `nearby-reference`로 원문을 붙인다. 교체된 주제도 뒤의 정정 검색에 반영해 `카레→우동→소바`를 함께 읽힌다. 직접 연결한 정정들은 예산 축소 때 하나씩 버리지 않는다. 명확히 다른 주제의 취소는 따라붙이지 않고, 대상을 해석하지 못한 지시어 정정만 최근 두 후보의 짧은 원문과 함께 `scope-caution`으로 둔다. 모두 `candidate-not-confirmed-state`이며 확정된 사실 갱신이 아니다. 연관 없는 취소 25개가 사이에 있어도 관련 메뉴 기억이 그 분량 때문에 사라지지 않는 단위 검사를 둔다.

이 규칙은 같은 단어가 서로 다른 약속에 쓰인 경우를 혼동하거나 우회적인 정정 표현을 놓칠 수 있다. 일반적인 의미 해석이나 시간 그래프를 구현했다고 보고하지 않는다. 원문을 계속 보존하므로 검토 후 더 나은 정정 연결기로 다시 색인할 수 있다.

모델 입력은 다음과 같다.

```text
system: 문자 규칙 + 인물 관계/목표/판단/말투 카드 + 일상 IF 범위
user/assistant: 최근 실제 성공 교환
user: JSON으로 구분한 과거 원문 구간·정정 후보·허용 사실·다른 시점의 참고 장면
      + 별도 JSON 문자열인 방금 받은 실제 문자
```

이전 `user` 발언은 사용자가 그때 주장한 말이고, `assistant`의 `사올게`는 제안/약속이다. 이를 구매 완료로 변환하는 코드가 없다. 프롬프트는 정정 우선, 원문 시간·발화자 유지, 모호한 대상 확인을 요구한다. 실제로 잘 읽는지는 생성 결과를 확인해야 한다. 관련 자료를 넣었다는 사실만으로 그 조건을 모델이 지켰다고 판단하지 않는다.

[Thinking 실행 계약](THINKING.md)에 따라 Gemma native template의 토큰 수가 입력 예산 3,072를 넘으면 장면→낮은 순위 사실→과거 기억 묶음→오래된 최근 교환 순으로 제거한다. 기억의 원래 약속만 남기고 정정만 버리지 않도록 구간과 정정 전체를 같은 묶음으로 제거한다. system·현재 문자 자체가 안 들어가면 오류로 처리하고 몰래 자르지 않는다.

핵심 관계는 인물 카드의 명시적인 `relationship_refs`로 선택하며 검색 상위 K 밖에서도 system에 유지한다. 검색 자료와 같은 승인·인물·시나리오·split 검증을 적용하고 중복 검색에서는 제외한다. 고정 관계와 현재 문자조차 예산에 들어가지 않으면 오류로 처리한다. 승인된 IF 시작 위치(하루카=나팔꽃, 마지마=카무로쵸)는 원작 사실과 구분하며 이후 대화의 실제 이동과 정정이 우선한다.

원문 ID, system·현재 입력 envelope 스냅샷, 채택 근거와 검색 버전, native 토큰 수, 제외한 ID, 정확한 입력 SHA를 저장한다. `reconstruct_input`은 원문 ID로 실제 입력을 재구성하고 SHA를 검사한다. 전체 이력 사본을 생성 실행마다 저장하지 않는다.

## 검사와 아직 증명하지 않은 부분

- CPU 단위 검사는 원문 불변, 다른 범위·실패 이력 거부, 정정 동반, 예산 때문에 정정만 탈락하지 않음, 원문 해시 기반 재구성을 확인한다.
- `retrieval-dev.json`의 40문항은 개발용이다. 결과를 본 뒤 한국어 조사 stopword 오류를 고쳤으므로 독립 holdout이라고 부르지 않는다. 처음 결과와 실패 사례는 숨기지 않는다. 별도 작성자가 구성한 미사용 문항의 통과 여부가 최종 검색 gate다.
- `dialogue-evaluation.json`은 인물별 10개 × 6턴, 인물별 30턴 대화, 같은 마지막 문자에 다른 조건을 주는 4쌍의 실행 입력과 판정 기준이다. 파일이 있다고 검사를 통과한 것이 아니다. 쌍은 두 조건을 모두 적절히 답한 수로도 기록한다.
- 방금 받은 문자에 유효한 `YYYY-MM-DD`가 있으면 Asia/Seoul 날짜로 비교해 과거 검색의 중심 교환을 제한하고 적용 날짜를 입력에 표시한다. 주변 문맥과 이후 정정은 그 날짜 밖이어도 함께 읽힌다. 시각 미상인 원문은 특정 날짜라고 추정하지 않는다. `지난주` 같은 상대 날짜를 절대 범위로 바꾸는 자연어 파서는 없다. 여러 달·수천 교환의 성능과 복합 사건의 시간 추론은 아직 검증 대상이다.
- 임베딩 캐시가 비었거나 서버가 재시작했을 때 과거 후보를 다시 인코딩하는 비용, 직접 관련된 정정 자체가 매우 많아 기억 묶음 전체가 예산에서 빠지는 경우, 구어체 지시 대상과 모호한 부정을 놓치는 경우를 별도로 관찰한다.
- 모델의 말투·판단·관계/감정·지식·문맥/기억·문자 형식을 각각 검토한다. RAG 검색 성공률을 인물 재현 정확도로 바꾸지 않는다. 팬 검토는 미완료다.

```sh
PYTHONPATH=ai python -m kiryu_ai.chat_retrieval \
  --download-embedding .tooling/gemma/embeddings
PYTHONPATH=ai python -m kiryu_ai.chat_retrieval \
  --registry ai/chat/registry.json --evaluation ai/chat/retrieval-dev.json \
  --embedding-dir .tooling/gemma/embeddings --output /tmp/retrieval-dev-result.json
PYTHONPATH=ai python -m unittest discover -s ai/tests -p test_chat_prompt.py -v
```

## 폰 초기화와 기록 보관

설정의 **처음 상태로 되돌리기**를 확인하면 브라우저에 새 초기화 경계를 저장하고,
다음 AI 연락처 진입 시 새 익명 세션(새 방문자 ID)을 발급받는다. 하루카·마지마의
최근 대화와 장기 기억은 새 방문자 범위에서 시작하며, 기존 원작 RAG·인물 카드·기본
시작 장면은 그대로 사용한다. 초기화는 모델 학습이나 원작 지식을 지우는 작업이 아니다.

이전 SQLite 방문자·대화·요청·생성 결과·검토는 삭제하거나 수정하지 않는다. 관리자
화면에서는 이전 방문자 기록으로 계속 조회할 수 있지만 새 세션의 이력·기억 검색에는
포함되지 않는다. 초기화 전 접수한 작업이 늦게 완료되어도 이전 방문자의 기록에만 남는다.
기존 토큰 자체를 서버에서 폐기하는 기능은 아니며, 이 브라우저는 그 토큰을 재사용하지 않는다.

초기화 경계는 단일 localStorage 쓰기로 확정하며 저장 실패 시 전체 초기화를 중단하고
확인창에 오류를 표시한다. 옛 비동기 응답은 경계 검사로 버리고 다른 열린 탭도 storage
이벤트로 전환한다. 취소한 경우 세션은 유지된다. 초기화 직후 서버가 꺼져 있어도 이전
대화를 복원하지 않으며, 연결이 복구되면 새 세션을 자동 발급한다.
