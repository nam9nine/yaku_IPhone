# 답장 알림

문자 전송 후 요청마다 정한 10~20초의 대기가 지나면 타이핑을 표시한다. 완성 답장은 생성 완료 시각에 같은 대기를 더한 뒤 전달하며 타이핑 최소 1.5초를 보장한다. 모델의 생성 한도나 품질 판정과 별도의 화면 연출이다. 새로고침으로 대기 시간을 다시 뽑지 않는다.

## 방문자가 켜는 방법

1. iPhone Safari에서 기존 사이트를 연다.
2. 공유 메뉴의 **홈 화면에 추가**를 선택하고 추가한 앱을 연다.
3. 하루카나 마지마 대화의 **답장 알림 설정**에서 **알림 켜기**를 누르고 OS 권한을 허용한다.

지원되는 데스크톱 브라우저는 홈 화면 추가 없이 허용할 수 있다. 알림을 끄거나 미지원인 경우 사이트 안의 배너·읽지 않은 표시를 사용한다. 브라우저가 중단된 상태의 알림에는 OS 구독이 필요하며, 모델을 실행하는 Mac과 Tunnel은 켜져 있어야 한다.

iPhone·iPad의 설치된 웹 앱에서는 기기의 상태표시줄을 사용하고 웹 상태표시줄과 예약 공간을 숨긴다. 기존 safe area는 유지하며 일반 브라우저·데스크톱 표시는 유지한다. 이 분기는 합성 standalone 환경에서 검사했고 실제 iPhone의 OS 상태표시줄·viewport는 별도 확인 대상이다.

## 저장과 전달

- 일반 문자 DB와 별개로 로컬 상태 폴더에 `push.sqlite3`, VAPID 키를 소유자 전용 권한으로 보관한다. 관리자 대화 내보내기에 구독 endpoint·인증키·개인키를 넣지 않는다.
- 브라우저의 익명 세션 토큰으로 구독 등록·해제를 인증한다. 현재 방문자에게 속한 정상 완료 요청만 알림 대상으로 삼는다. 구독 이전에 끝난 과거 답장을 일괄 발송하지 않는다.
- 구독별 진행 위치와 `(subscription_id, job_id)` outbox를 사용한다. 유한한 재시도·만료·동일 notification ID와 브라우저 중복 방지를 함께 적용한다. 외부 Push 서비스가 받는 시점까지 완전한 한 번 전송을 보장하지 않는다.
- HTTPS의 허용된 Apple·Google·Mozilla Push 호스트만 수신 주소로 받는다. 키 길이·곡선과 공개 DNS 주소를 확인하고 redirect를 따라가지 않는다.
- 초기화는 IndexedDB의 세대를 바꾸고 binding을 폐기한 뒤 진행한다. 다른 탭의 늦은 등록 응답과 이전 방문자 Push를 거부한다. 서버 해제가 일시 실패해도 브라우저의 무효화 경계를 먼저 보존한다.
- Service Worker는 캐싱 없이 Push만 처리한다. 알림 클릭은 고정된 사이트 경로와 하루카·마지마 대화만 연다. 알림은 최종 답장의 짧은 미리보기를 포함한다.

## 플랫폼 근거와 한계

[WebKit iOS Web Push 안내](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)에 따라 홈 화면 설치와 사용자 동작에 의한 권한 요청을 사용한다. [WebKit userVisibleOnly 설명](https://webkit.org/blog/12945/meet-web-push/)에 따라 유효한 Push는 foreground에서도 OS 알림을 표시한다. OS 구독이 켜졌으면 앱 안의 별도 배너·소리를 꺼 중복을 줄인다.

권한·OS 집중 모드·브라우저 종료 정책·Mac 가용성은 알림 시각에 영향을 줄 수 있다. 브라우저 자동 검사와 암호화 transport 검사는 실제 iPhone 잠금 화면 수신 검증을 대신하지 않는다.
