# 문자 대화의 자연스러움 (Issue #133)

키류 답장 선택지와 하루카·마지마 문자의 흐름이 부자연스럽다는 피드백을 입력 맥락·프롬프트 구조·생성·선택지·발신 타이밍 단위로 다룬다. 응답 속도는 판단 기준에서 제외한다(2026-11-02 사용자 결정). 하루카와는 앞으로 채팅하지 않고 마지마·키류의 말·다테 같은 인물에 집중한다(2026-11-03 사용자 결정). 이 문서의 하루카 관련 변경(선택지 문구, 저장 검증 버그 수정)은 지금 화면을 위한 것이며, 하루카 AI 답장의 제거나 다테 대화 추가는 별도 작업이다. 실제 출력 비교는 아래 [평가](#평가)에 기록하며, 팬 검수를 대신하지 않는다.

## 관찰한 원인

운영 DB 백업 사본(2026-11-02)의 집계다. 방문자 원문은 저장소에 옮기지 않는다.

- 최근 프롬프트(v20–v34) 마지마 답장 14개 중 43%에 `갑자기`, 64%에 `키류쨩`이 들어갔다. 짧은 `네` 3번 중 2번은 대답이 짧다고 나무랐다.
- 방문자가 화면의 도입 문자에 `안녕`·`네`로 답하면 모델은 대화가 갑자기 시작된 것으로 받아들였다. 도입 문자와 로컬 후속 문자는 모델 입력에 대화로 들어가지 않았다.
- 시스템 입력은 약 3,000자의 추상적 금지 규칙 위주였고 현재 문자는 빈 참고 JSON에 싸였다.
- 하루카 선택지가 `메모에 적힌 …`, `오늘 할 일에 적힌 …` 같은 UI 표현이었고 직전 확인 문자에 답하지 않았다.

## 알려진 제한

- 마지마에게 직접 건 통화를 12초 안에 끊거나 받지 않을 때 앱이 붙이는 로컬 문자는 문구가 모델에 전달되지 않고 이벤트 설명만 전달된다. 문구가 호감도와 통화 순번으로 정해지기 때문이다. 문구별 이벤트 ID를 쓰려면 서버 카탈로그가 Pages보다 먼저 배포돼야 한다.
- 하루카 AI 답장을 기다리는 동안 다른 할 일을 체크하면, 화면은 시간순으로 보여 주지만 모델은 그 확인 문자를 다음 요청의 키류 문자 앞에 둔다. API에 체크 시각이 없다.
- 새 하루카 선택지(`*-mild`, `*-sunset`, `*-stay`, `*-tight`)를 보낸 방문자의 저장 하루는 이전 Pages로 되돌리면 이전 검증에 걸려 초기화된다.
- 평가 상황은 합성이며 팬 검수를 대신하지 않는다. 판정 호출도 같은 Gemma 모델이다.

## 운영 설정

`python -m kiryu_ai.chat_server`는 기본 후보 3개로 실행한다. `--reply-candidates` 또는 `KIRYU_REPLY_CANDIDATES`(1–5)로 바꾼다. 다른 호출자가 직접 만드는 `ChatService`의 기본값은 1이다. 후보마다 모델 호출 제한(입력+생성 6,144토큰, 120초)은 그대로이며, 여러 후보는 한 생성 슬롯에서 순서대로 실행된다.

## 평가

`kiryu_ai.naturalness_evaluate`는 `ai/chat/naturalness-evaluation.json`의 합성 다중턴 상황을 실제 모델로 재생하고 모델 답장을 다음 턴의 이력으로 쓴다. import가 절대 경로라 같은 파일을 이전 체크아웃의 `ai/`에 대해 실행해 버전을 비교할 수 있다. 운영 manifest의 복사본과 새 출력 폴더를 쓴다.

```sh
PYTHONPATH=ai .tooling/gemma/venv/bin/python -m kiryu_ai.naturalness_evaluate \
  --manifest /tmp/evaluation-manifest.json \
  --api-key-file .tooling/gemma/model-api-key.txt \
  --embedding-dir .tooling/gemma/embeddings \
  --output /tmp/naturalness-run --choice-set after --samples 3 --thinking on
```

볼링 사건 경로는 `kiryu_ai.episode_evaluate --reply-candidates 3`으로 같은 후보 선택을 적용한다. 이 경로는 실제 API를 띄우며 manifest 폴더의 모델 파일 해시를 확인하므로, 복사본이 아니라 원본 `runtime-manifest.json`을 읽기 전용으로 지정한다.

사고 OFF 비교: 같은 프롬프트(v37)로 사고 ON/OFF를 같은 방식으로 판정하면 5:5였다. OFF는 `그렇군요`에 덜 나무랐지만 답장이 길고(평균 51.6자) `웬일로` 반복, 평소 존댓말 지적, 의미가 어긋난 문장이 늘어 사고 ON을 유지한다.

볼링 사건 회귀: `bowling-evaluation.json`의 4개 상황(애매한 `음…`, 거절, 부상, 수락 후 취소)을 main 코드(후보 1개)와 이 변경(후보 3개)으로 실제 API·DB에서 실행했다. 20개 기록이 모두 완료됐고, 사건 단계와 결정은 19개가 같았다. 나머지 하나(거절 뒤 `오늘은 그냥 문자만 하죠.`)는 결정 이름만 `no_change`/`defer`로 달랐고 두 쪽 모두 종료 단계를 유지했다. 이 변경의 답장은 짧고 `키류쨩`이 적었지만, 거절·취소 뒤 후보가 카드 예시 3을 그대로 베꼈다(한 턴은 후보 3개 모두). 그래서 예시를 그대로 옮겨 쓸 수 없는 구체적 상황으로 바꾸고, 예시와 거의 같은 답(유사도 0.8 이상)은 탈락시켜 새 후보를 만들게 했다. 이 버전(v41)으로 거절·수락 후 취소 2개 상황과 일반 문자 쉬기·바쁨 2개 상황을 다시 실행한 결과, 예시를 옮긴 답장은 없었고 사건 단계는 앞 실행과 같았다.

개발 중 관찰: 검토 전 초안(v35)은 `키류쨩`을 거의 쓰지 않았고(0/24) 예시 문장을 그대로 베꼈다. 턴 안내·장면에서 키류의 대답을 '짧다'고 묘사하면 `그렇군요` 뒤 후보 대부분이 길이를 탓했다(v37·v38에서 한 턴의 후보 5–6개 모두). 그래서 대답을 그대로 인용하고, 불평 제거를 마지막 안전장치로 두었다.
