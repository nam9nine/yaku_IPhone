# 키류–마지마: 실행용 관계와 원작 회상

Issue #88은 두 인물의 관계만 보완한다. 사용자는 키류이며 답변자는 마지마다. 모든 관계·사건을 알고 있다는 선언이 아니라, 아래 근거를 `daily-if-v1`에 한정해 채택한 것이다.

| ------------- | --------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 키류 → 마지마 | `마지마 형님`, `형님`은 익숙한 존중의 호칭. 부름 자체를 갑작스러운 예의·도발·불쾌함으로 해석하지 않는다.                    | 사용자의 명시적 지정 + [한국어 게임 캡처](https://r563.tistory.com/9)의 키류 명패와 발화 직접 확인. 게임 빌드와 공식 번역판은 미확정.    |

호칭은 친형제·의형제 서약·현재 직속 부하 관계를 새로 설정하지 않는다. 마지마의 장난을 없애거나 모든 부탁을 수락시키는 규칙도 아니다. 과거 AI가 호칭을 잘못 부정한 발언은 원본 대화에 남지만 관계 설정을 덮어쓰는 근거로 삼지 않는다. 잘못된 전제를 짧게 바로잡는 반응은 원작 대사가 아니라 이 프로젝트의 IF 운영 해석이다.

카드의 안부·관계 정정 문답 두 개는 작성자가 만든 IF 예시다. 원작 대사·학습 자료·현재 대화 이력이 아니며, 내용을 사실로 기억하거나 문장을 그대로 반복하도록 지시하지 않는다. 익숙한 연락을 받아들이고 자기 착각을 바로잡는 방식을 보여 준다.

## 자료와 실제 검색을 구분하기

`cards.json`의 호칭·관계 2개는 `relationship_refs`로 매 답변에 들어간다. 두 과거 사건은 고정 입력에 넣지 않고 검색 후보에 둔다. 이 구분으로 기본 모델 지식이나 고정 프롬프트의 답변을 RAG 성공으로 잘못 세지 않는다.

참고 장면은 요약뿐 아니라 원래 화자·상대·시점·대사까지 검색한다. 장면은 실제 user/assistant 이력으로 변환하지 않는다. 다른 인물·시나리오·평가 분할은 색인 전 필터링한다. 검색 뒤에도 최종 토큰 예산에 살아남은 근거를 확인한다.

원문·추출문·해시·범위는 `registry.json`에 연결되어 있고, 큰 원본은 ignored `references/local/gemma-chat/relationship88-research/`에 있다. 한국어 캡처는 기존 `verified_quote`, `training_eligible=false` 판정을 유지하며 이번 호칭 자료를 학습 대화로 승격하지 않는다. 팬 검수는 별도다.

## 검증 기준

- 새 대화의 짧은 부름·존댓말·평범한 부탁과 잘못 답한 뒤의 정정 요청을 각각 검사한다.
- 검색에서 찾은 ID, 실제 최종 입력의 ID, 답변의 사실·주체·시점·불확실성을 따로 확인한다.
- 동성회 복귀와 건설 도움, 자료에 없는 구체적인 기억을 함께 검사한다.
- 원문 회수 성공만으로 인물 재현·다중턴·전 시리즈 스토리 이해 완료를 주장하지 않는다.

## 생성 근거를 확인하는 방법

검색에서 정답 자료를 가져왔더라도 모델이 답변에 원인·횟수·현재 상태를 추가할 수 있다. 운영 후보 v7에는 확인된 과거 행동·동기까지만 말하고 세부를 덧붙이지 않는 지침을 둔다. 별도 v8 실험에서는 행동·동기·시점·완료 상태를 하나씩 대조하는 절차를 추가했으나, 일부 상태 경계 개선과 익숙한 연락에 대한 반응 악화가 함께 관찰되어 채택하지 않았다. 어떤 일을 결의했다는 자료만으로 완료도 미완료도 확정하지 않는 것은 계속 평가할 기준이다.

실험과 평가는 [FActScore](https://aclanthology.org/2023.emnlp-main.741/)의 주장별 근거 평가 관점, [Microsoft의 RAG 프롬프트 지침](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/rag/rag-prompt-engineering)의 근거 범위·정보 부족 시 대응, [Google의 예시 사용 지침](https://ai.google.dev/gemini-api/docs/prompting-strategies)을 참고했다. 해당 논문의 평가기나 다단계 검증 파이프라인을 구현한 것은 아니다. 검색 회수율·답변 근거 충족·말투·팬 평가는 서로 다른 결과다. 근거 밖 과거 설명과 일부 생성 잘림은 [Issue #93](https://github.com/nam9nine/yaku_IPhone/issues/93)에 남기며, 이 변경으로 RAG 답변의 충실성이 완성됐다고 표시하지 않는다.
